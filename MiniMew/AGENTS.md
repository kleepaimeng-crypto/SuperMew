# MiniMew 学习与实现约定

本文件继承上级 `../AGENTS.md`，适用于 `MiniMew/` 内的工作。这里是用户明确要求的分阶段复现学习目录。开始时先读 [AGENT_HANDOFF.md](AGENT_HANDOFF.md)，再读 [LEARNING_PLAN.md](LEARNING_PLAN.md)；目录导航见 [README.md](README.md)。

## 学习者基础与重点

- 用户有 Java/Spring 开发经验，有 Python/FastAPI 基础但不深入。
- 用 Spring 的熟悉概念解释 Python/FastAPI 的相同职责与关键差异，避免逐语法重讲。
- 重点是后续 Agent、RAG、持久化执行、恢复与评测；基础工程只深入到后续实现所需程度。
- 不假定 Java 经验代表已理解 Python async、依赖注入生命周期、数据库事务或 Agent 状态管理。

## 必须遵守的互动门槛

用户要求：频繁询问与提问，确保理解后，才开始对应阶段的代码编写。

1. 每个阶段先讲目标、前置知识、首次引入的工具/库、首次引入的架构概念、实施顺序和验收场景。
2. 拆成短小讨论单元，每轮通常只提出 1–2 个理解题。问题优先要求解释具体场景的行为或原因，不只问“懂了吗”。
3. 用户回答前，不进入依赖该回答的实现。用户提出问题或理解存在缺口时，先解释、举例并换一个场景复核。
4. 不能把沉默、经过一段时间、背景调查回答、机械重复术语或一次笼统“懂了”当作已通过全部理解检查。
5. 编码前说明具体的小步范围。用户已通过该范围的理解检查且明确表示开始后，才编写该范围代码；一次授权不代表后续未讲解阶段也获准编码。
6. 阶段过大时可分成子步骤，每个子步骤单独讨论、确认和实施，不要求用户一次掌握全部细节。
7. 编码之后讲解数据流、关键取舍、验证结果与失败行为，再检查理解并记录实际进度。
8. 不能承诺判断用户内心是否“完全理解”；以用户自己的解释、场景推演和明确反馈作为可观察依据。拿不准时继续讨论。
9. 文档计划与真实对话记录可以先写；未获对应授权时，不创建应用骨架、依赖 manifest、迁移、生成代码、配置文件、测试代码或运行安装脚手架命令。
10. 只有用户之后明确改变上述学习方式，才调整门槛。

## 大章节的计划、总结与代码框架

用户于 2026-10-30 补充以下约定，即日起纳入学习与开发流程：

- **章节口径**：大章节默认对应 LEARNING_PLAN.md 的九个一级阶段；1.1、2.1、2.2 等为章内子项。用户明确调整章节范围时按其要求执行。
- **开始前先列子项**：每开始一个新大章节，先在对话中给出本章的子项编号、目标、实施顺序与依赖、各项技术职责和验收结果，再写入 `chapters/NN-章节名称.md`。区分沿用技术与新引入技术，说明本章与现有模块如何衔接。子项计划改变时记录调整原因并同步文档。
- **结束时保存文字总结**：每结束一个大章节，必须在同一章节文档中保存中文总结，说明本章实现了什么、关键概念和取舍、完整数据流、主要失败场景、实际验证及尚未完成的边界。聊天中的总结不能替代文件记录；不把计划或 fake 验证写成已交付或真实在线能力。
- **结束时梳理代码框架**：基于当时的真实源码列出业务目录/模块，逐项说明职责、调用关系、数据与状态由谁保存，并选一条代表性请求或任务走读相关文件。重点是“每一部分做什么、为什么存在、如何协作”，不逐行讲语法。区分已经实现和后续规划，标注总结日期与覆盖范围，文件链接使用仓库相对路径。
- **理解与授权沿用原约定**：章节计划和总结均不扩大应用编码授权；章内仍按理解检查通过、明确授权的小步推进。框架复盘的问题以职责、数据流和失败行为为主，不要求背诵语法。

章节文档使用 [CHAPTER_TEMPLATE.md](CHAPTER_TEMPLATE.md) 的结构，实际创建时按本章内容填写；尚未发生的总结、验收和理解反馈不能预填完成。AGENT_HANDOFF.md 继续保存唯一的当前学习进度与授权边界，章节文档保存计划和带日期的总结，不再维护一套独立进度状态。

## 按业务职责整理代码

- 用户允许在文件结构混乱、业务职责交叉或可读性差时进行必要整理。先读现有实现，说明具体问题、拟调整结构与影响范围，再在 MiniMew 内按业务职责移动、拆分或重命名；不为套用分层形式创建空目录或重复实现。
- 结构整理保持既有行为、领域不变量和正式入口；同步修正 import、测试、脚本、生成器入口、文档导航及章节代码框架中的路径。生成物仍从真源生成，已执行迁移的历史不因目录美化而重写。
- 按影响范围验证整理前后的行为，保留用户未提交修改。若涉及新增功能或改变领域行为，先讲清变更并遵守对应小步的理解与授权要求；结构整理授权不等于开始尚未授权的执行器或 Agent/RAG 功能。

## AI 编程测试策略

用户于 2026-10-30 明确要求减少功能开发中的无效验证耗时，MiniMew 日常开发遵守以下规则：

1. 修改前先分析影响范围，不要默认执行全量测试。
2. 优先运行与改动直接相关的测试。
3. 涉及事务、并发、状态一致性时，扩大集成测试范围。
4. 只有发现回归风险或涉及核心模块时，才运行完整回归。
5. 不允许为了追求测试通过而修改或删除原有断言。
6. 报告必须区分新增测试、重复执行、实际通过、跳过和未执行。
7. 不要为了形式上的完整性重复执行已经通过且没有代码变化的测试。

执行时采用以下口径：

- 修改前简要说明受影响的入口、调用方、关键不变量与拟运行的用例；扩大范围时说明具体风险。认证与权限、Run/Message/Event 终态、共享持久化逻辑、Contract 和数据库迁移属于核心范围。完整回归需明确是受影响模块还是整个 MiniMew，不自动扩展到上级 SuperMew；上级明确要求的跨模块或发布门禁仍须按对应 Runbook 执行。
- 复用已通过结果前，确认相关源码、测试、依赖、配置、数据库结构与运行环境未变化；这些条件变化或出现新失败时，重新判断受影响范围。引用旧结果要标注原运行记录，不计作本轮新通过。
- 新增/修改的测试属于变更记录，首次/重复执行属于运行记录，通过/失败/跳过属于执行结果，分别列示，不能相加冒充用例总数。跳过指已收集但未执行的用例，未执行指本轮没有运行的检查；两者均说明原因。记录实际命令、结果及重复执行的原因。
- 纯文档改动只检查本轮差异、链接和格式；若文档修改了可执行命令或使用约定，再按其影响核对入口，不默认启动数据库、浏览器或模型检查。

## 工作边界

- 当前阶段与实际编码授权只以 AGENT_HANDOFF.md 的当前检查点为准；不得将一个小步的授权扩展到后续步骤。
- 只在本目录建立学习资产与之后明确授权的练习实现；不修改上级 SuperMew 的应用源码或覆盖其未提交修改。
- 后续 MiniMew 实现须有独立入口、依赖和配置，不能挂进 SuperMew 的路由、import 路径或生产执行链。包名、端口、数据库、数据目录与运行命令在编码前讨论确定。
- 不把此练习目录理解为已建立独立 Git 仓库；不自动 `git init`、commit 或 push。
- 领域术语与不变量参照上级正式文档；学习计划不改变 SuperMew 的 Contract 或 ADR。
- 不因学习简化而建立第二条聊天执行路径、静默 fallback，或把假数据检查描述为真实模型质量证明。
- 各阶段库与版本仅为待确认方案；依赖实际引入前核对兼容性，再由 uv/npm 更新独立 manifest 与锁文件。
