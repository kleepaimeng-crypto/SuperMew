### 首批资料范围与 RAG 链路位置（2026-11-09）

用户选定首批资料为 Markdown/TXT。这个选择限定本章最小解析范围，不表示已创建解析器、依赖或应用代码；PDF、Word 与 OCR 不纳入首批实现。

本章承担 RAG 的入库/索引链路：源文件 → 解析 → 分块及来源元数据 → Embedding → 候选索引 → 核验发布。第五章承担查询时的检索与生成链路：问题 → 编码/检索已发布片段 → Evidence → 模型回答与引用；第六章在同一正式入口扩展检索/评判策略。

- 解析把 Markdown/TXT 的标题、正文、段落等转成可处理文本及结构，同时保留原文定位关系。
- 分块决定检索最小片段的内容边界，需要尽量保留条件、结论与标题上下文；字符/Token 长度上限只是边界约束，不等于语义完整。
- 入库阶段保存文档/版本/chunk/章节或位置/内容 hash 等来源身份；查询时把相关片段及身份作为 Evidence 交给回答流程，再生成并核对引用。入库来源记录和答案中的引用展示属于不同环节。
- Job、Worker、租约和发布目录提供工程可靠性；分块、编码与检索策略影响找到的知识和回答质量。

例子：原文“仅限出差期间：餐费每人每天最多报销 150 元”。如果条件与额度被切开，单独召回额度可能丢失适用范围。下一轮围绕这个例子讨论分块边界，不预设固定块长或直接安装 splitter。

依据：[LangChain 官方知识库教程](https://docs.langchain.com/oss/python/langchain/knowledge-base) 展示加载、切分、向量化、索引及检索接入 RAG 的关系；项目中的领域身份与发布边界仍以 CONTEXT/ADR 为准。

### Markdown/TXT 分块与 Embedding 讨论（2026-11-09）

首批分块方案拟采用“结构优先、长度约束、必要重叠”：Markdown 优先沿标题层级组织章节，TXT 优先识别段落；过长章节再按段落/句子递归切分，最终受编码模型输入预算约束。短的适用条件和结论尽量一起保留，每块记录标题路径及原文位置；检索/回答时携带相应上下文。相邻块少量重叠有助于缓解边界丢失，但不保证语义完整，也增加索引体积与去重成本。具体字符/Token 预算、重叠量和 splitter 依赖尚未选定，不预填固定参数。

原文和来源定位必须保留；附加标题路径属于检索/回答上下文，不能把拼接后的偏移冒充原文件位置。条件跨块的失败案例要进入固定样例，后续再讨论父块展开，不提前实现第六章 Auto-merging。

Embedding 模型把文本编码为向量，用于相似检索；Milvus 执行向量搜索并返回原片段和来源身份；当前 DeepSeek 聊天模型接收检索证据后组织自然语言回答。入库为片段编码，查询时也要用兼容编码方式为问题编码，在同一可比较空间检索。具体模型/API、revision、维度与 query/document 入口待选型，不能仅凭向量维度相同假定任意模型兼容。

依据：[LangChain text splitters](https://docs.langchain.com/oss/python/integrations/splitters/index) 的结构/递归切分说明；[Sentence Transformers 语义搜索](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html) 的文档/查询编码流程。本节是拟定设计与知识讨论，尚无实现或效果验收。

### Embedding 运行方式选择（2026-11-09）

选型先区分运行位置，再确定服务/模型。两种路线均通过单一 Embedding Adapter 接入正式构建与查询，不建并行事实来源，也不在故障时静默切换模型。

| 路线 | 需要准备 | 取舍 |
| --- | --- | --- |
| 本机推理 | 模型权重、固定 revision、缓存与 Python 推理依赖；结合实际 CPU/GPU/RAM 选模型 | 编码文本可留本机，资源占用和维护由本机承担；不默认下载大模型 |
| 远程 API | 明确的 Embedding 服务和模型、凭据、网络策略、调用预算与限额 | 省去本机模型推理部署，文档片段/查询会发送给该服务；费用与可用性依服务确定 |

现有 DeepSeek 聊天配置保持回答职责，Embedding 配置独立选择。文档/查询编码通常使用同一模型及其规定的配套编码入口；任何替换必须验证向量空间兼容性，不能仅看维度。用户现已选择本机运行路线，并要求项目提供轻量模型与 BGE-M3 的选择；远程 API 保留为开章时的比较记录。拟提供两个独立 Embedding 预设，默认预设与兼容重建语义待确认，本节不授予下载、安装、配置或代码实现授权。

参考：[Sentence Transformers Quickstart](https://www.sbert.net/docs/quickstart.html) 展示同一模型的 query/document 编码与向量相似度计算；[Hugging Face TEI](https://huggingface.co/docs/text-embeddings-inference/index) 展示模型推理服务的部署职责。本轮只核对能力，不选择具体 SDK/模型版本。

### 本机 Embedding 候选与资源预算（2026-11-09）

本机路线已确定，首批为 Markdown/TXT。建议轻量中文 BAAI/bge-small-zh-v1.5 作为起步候选，BGE-M3 作为后续较重对照；两者尚未由用户最终选定，不先冻结模型/revision 或安装依赖。

- [BGE 官方系列说明](https://bge-model.com/tutorial/1_Embedding/1.2.1.html) 列 small-zh-v1.5 为 24M 参数、约 95.8 MB；[模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5) 列 512 维。该权重大小不是运行内存。
- [BGE-M3 官方说明](https://bge-model.com/bge/bge_m3) 列 569M 参数、约 2.27 GB，支持多语言。CPU/GPU 时延和内存/显存需按实际片段长度、批量、精度测量，不承诺特定硬件吞吐。
- 轻量模型先 CPU 推理是本项目小规模学习建议；GPU 加速要安装匹配的 PyTorch 并实际验证可用，不能把显卡被驱动识别当成推理链路已通过。[Sentence Transformers 安装说明](https://sbert.net/docs/installation.html)
- 小规模学习可从现有 16GB 级机器启动轻量编码实验；整套 IDE/浏览器/API/PG/Redis/Milvus 并行开发建议 32GB 为工程余量判断。[Milvus 2.6 Standalone 要求](https://milvus.io/docs/v2.6.x/prerequisite-docker.md) 的部署环境内存要求为 8GB、建议 16GB，本章服务版本尚未锁定，届时再按选定版本核对。
- 安装/模型/缓存预留约 10–20GB 只是起步预算估算，不含不断增长的原文件与索引；按设备实际空闲选择磁盘，后续通过项目级配置管理，不能隐式写满系统盘。

真实设备读数和用户反馈只保存在交接，章节不依赖这台机器。当前没有下载、安装、模型试跑或性能验收，具体批量/长度/并发参数待选型后测定。

### 双模型预设与安全切换设计（2026-11-09）

用户报告另有 R7-9700X、RTX 5070、24GB 内存设备，询问 BGE-M3 运行条件、能否继续用轻量模型，并要求项目提供模型切换选择。首版拟增加轻量 `BAAI/bge-small-zh-v1.5` 与较重 `BAAI/bge-m3` 两个 Embedding 预设；两台设备都可显式选择预设和 CPU/CUDA 执行设备，硬件更强不强制使用更大模型。模型权重与本地缓存不随 Git 同步。

按标准桌面 RTX 5070 的 12GB 显存做小规模 BGE-M3 推理的可行性判断；另一设备未现场检查，实际显存、可用资源、驱动/PyTorch 兼容性及吞吐尚未验证。建议初测 FP16、512–1024 Token 上限、小批量例如 4，再据实测调整，属于起测建议，不是验收数据或最终冻结参数。[NVIDIA 桌面 RTX 5070 规格](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5070-family/)、[BGE-M3 官方模型卡](https://huggingface.co/BAAI/bge-m3)。5070 属 Blackwell，选择依赖时需核对 PyTorch 构建/驱动的支持，不能直接照搬旧 GPU 环境；具体软件版本在引入前验证，不预填已安装。

模型切换纳入本章 4.4、4.6、4.7 的最小范围，完整模型/能力控制面仍留后续章节：

1. 用正式 Embedding 配置入口保存预设身份、model ID/revision、维度、归一化、query/document 编码方式与相关输入预算；加入文档构建 fingerprint。现有 `model_control.py` 只拥有回答模型配置/Run answer snapshot，当前没有 Embedding 切换实现，不把新功能写成现有能力。
2. 模型选择表示目标构建配置；Index Job 接收时冻结构建配置，已接收任务不会随下拉框变化而改用新模型。查询使用已发布索引绑定的兼容编码配置，不直接使用“最后选择的模型”。
3. 同一知识库切换不同向量空间时，建立独立候选索引，重新编码范围内文档，精确核验后才发布切换。构建期间原已发布索引与原编码模型继续提供查询，失败维持原方案。完整切换范围及发布事务在 4.6 具体设计中明确，不允许只切部分查询端而混用旧向量。
4. UI 提供模型选择、当前生效模型、目标模型、重建进度与失败提示，操作表达为“重建并切换”。未准备好的本地模型显示明确状态，下载/加载过程显式管理，不在导入模块或普通查询中悄悄下载。
5. 已有兼容目标索引且与当前文档版本范围一致时可验证后复用；不承诺每次返回旧模型都无须构建。不同模型即使维度相同也不能据此判定兼容。只改变同一模型的 CPU/GPU 执行位置，且编码配置兼容时通常无需重建，仍需校验数值/检索一致性。

轻量模型 512 维，BGE-M3 Dense 向量 1024 维，不能写进同一个固定维度字段冒充直接切换；具体 collection/索引定位属于正式构建目录，不提供客户端任意选择检索 target 的入口。这里只使用 BGE-M3 Dense 能力，Sparse/ColBERT 与后续 Hybrid 不随模型预设一起提前实现。

### 4.1 工程包 A：文档目录与持久入库预留

| 交付项 | 本包具体范围 |

| Document Version | 一次不可变内容及冻结的构建配置/来源信息 | 不原地覆盖已经被引用的旧内容 |
| Index Job | 对该版本执行构建/发布等工作的进度、尝试与执行资格 | 不是用户提问的 Run，也不是依附某 HTTP 请求的内存任务 |
| 文件存储 | 不可变源文件/解析产物的明确版本范围 | 不决定当前可检索版本 |
| PostgreSQL Catalog | 文档/版本/Job 的持久事实和发布可见性 | 不代替向量相似度搜索 |
| Milvus | 带完整身份的向量、检索所需文本/元数据及索引 | 不通过“哪条最后写入”决定 current |
| 浏览器 | 当前界面与查询结果 | 不凭上传成功或进度百分比宣布版本已发布 |

所有 chunk/后续 Evidence 都要保留文档、版本、章节/位置与内容 hash 身份，不能只存文件名。数据所属用户由后端确定，检索条件由正式 scope 生成，不接受客户端任意指定他人归属或 candidate。

### 关键不变量与失败场景

- 上传接收、构建完成和发布成功是不同事实；只有发布后才进入正式检索范围。
- candidate 在核验/发布前不可检索；任何解析、Embedding、Milvus 或发布失败不改 current。
- 向量库与 PostgreSQL 之间不假设存在一笔可同时回滚的普通数据库事务；通过不可见候选、核验、原子 current 切换与精确清理处理失败。
- 同内容但 parser/chunker/Embedding/index 配置变化可能产生不同构建，fingerprint 必须覆盖实际构建配置；不能只看文件 hash。
- 每次任务写入检查执行资格；旧 Worker 不能发布，较早候选晚完成也不能覆盖较新候选。
- Worker 重试不会让 failed 版本重新变成 current；版本终态与任务的允许重试范围在模型设计中分别明确。
- Provider/存储故障明确报告，不能解释为“文档没知识”或悄悄切换未声明模型。
- 物理清理按精确版本范围执行，不按文件名或整个 Document 盲删；不删除仍为 current/pending 的产物。

### 4.1 首轮讨论：一份文档的三种身份

以《报销制度》为例：Document 表示这份制度的稳定身份；v1/v2 是它两次不可变内容；构建 v2 的 Index Job 负责把 v2 解析、分块、向量化并尝试发布。v2 上传成功、正在构建、构建失败，都不能自动把 current 从 v1 切成 v2。这个拆分也让后续答案引用可以定位“当时的制度版本”，而不是只能打开可能已被替换的同名文件。

### 已交付的数据链路

```text
认证用户提交 Markdown/TXT 和幂等键
→ 校验格式、UTF-8、体积及表单字段
→ 锁定本用户个人知识库，先查原提交
→ 新增 Document 或锁定指定 Document
→ 冻结构建配置（含源格式）并计算 fingerprint
→ 以版本 UUID 原子保存源文件
→ 同一短事务写 Version、Index Job、提交映射与 pending 指针
→ 提交后返回 202；复用原构建返回 200
```

源文件没有与 PostgreSQL 共用分布式事务。写失败时预留回滚；源文件已完整落盘而 DB 提交失败/结果不明时保留文件，避免删除实际提交成功的内容。孤立完整文件的受控清理使用与上传相同的版本级 advisory lock，并确认无任何版本记录后才删除，默认只列清单。已登记版本的文件全部保留，本包不做物理版本退休。

同一键不同正文/操作返回 409；同键重试优先返回原 Job，与后来默认配置无关。相同文档的 current/pending 相同内容和构建可复用，新增独立 Document 不按内容或文件名强制合并。失败/被替代版本不会复活。相同字节按 TXT/Markdown 解析可能不同，因此源格式进入不可变构建配置和 fingerprint。新版预留及失败不改变旧 current。

新建的个人知识库保存目标构建快照；现有库不随环境变量改变。`GET /v1/embedding-profiles` 展示两个本地模型的元数据，没有加载/下载权重。配置初始分块预算为轻量 384/48、M3 768/64（chunk/overlap Token），是下一包遵守并用案例验证的版本化起点，不代表已测的最优策略；更改配置将产生不同构建身份。API 不接受客户端任意模型 ID/路径或 owner 字段。

任务领取 Repository 使用 Document → Job 锁顺序、SKIP LOCKED、数据库时钟 lease 和递增 execution fence；只有 fingerprint 匹配的候选任务可被领取。过期后可由新 owner 领取，旧 owner 的心跳/进度/失败写入被拒绝，失败终态只成功一次。源码没有独立消费进程，本包真实上传后的任务保持 pending。

### 实际数据流与代码地图

```text
不可变源文件 + 源 hash + 版本/构建身份

→ Markdown 顶层结构/TXT 自然段，章节/父节/代码/表格

→ 原文切片 + 附标题编码文本 + hash/稳定 chunk ID
```

| 源码 | 实际职责 |
| --- | --- |

原文坐标是 Unicode code point 的 0-based `[start,end)`，行号为 1-based 且包含末行，不是 UTF-8 字节或 JS UTF-16 下标。BOM/CRLF 不从原文中删除/改写；解析器输入及行映射另行处理。source_text 精确对应原文切片，embedding_text 另附标题，二者各有 hash。代码里的标题形状不产生章节；引用链接定义等剩余原文也保留，不在解析后丢掉内容。

普通段落/列表优先合并结构边界，超长时优先句子/换行，再按 Token 原文边界拆；目标 384（含标题与特殊 Token），正文 overlap 最多 48，必要时减少以保证每次向前。不同章节、代码/表格间不机械重叠。代码/表格及包含它们的嵌套结构保持完整，超长则明确失败；标题太长或只有标题无正文也明确失败，不隐去或截断后伪装成功。父章节的内容范围和关系已保留，但语义条件/远处例外不自动补入子块；第五/六章仍需按预算展开检索上下文。

### 新知识：manifest 不只是数量

假设预期 chunk ID 为 A/B/C，实际写入 A/B/X，两边都是 3 条，仍缺 C 且多 X。manifest 是构建应有产物的精确清单，核验要比较身份及相关 hash/元数据，不能只检查条数或向量维度。即使候选核验通过，B 也不改变 current；发布成功是之后独立的持久事实。

### 首个关键边界：构建好与正式发布
