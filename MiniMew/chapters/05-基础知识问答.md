### 本章目标与范围

让现有Run中的模型能够提出知识检索请求，由服务端授权并执行已发布范围内的检索，将可定位的证据返回模型，最终生成带引用的答案。普通聊天继续走同一Thread/Run/Message/Journal路径；文档检索复用第四章，不另建绕开持久执行的聊天入口。

先完成最小Agent工具循环与Dense知识问答。复杂RAG路线、BM25/RRF/重排/自动合并/证据评判与改写在第六章；HITL/持久Checkpoint恢复在第七章；评测工作台在第八章。当前沿用个人用户/知识库隔离，不新增组织租户体系或GPU/M3运行能力。

### 沿用技术与新增概念

- 沿用FastAPI、Pydantic、SQLAlchemy/PostgreSQL、Run/Event/SSE、LangChain模型Adapter、DeepSeek关闭思考配置、本地BGE轻量编码与Milvus。前端仍用Vue/Pinia，工程接线集中交付。
- 新增Tool calling、工具Schema、工具结果消息、Agent有界循环：模型给出工具名和参数，由程序执行，再将结果交给模型。它们不是新的数据库服务，也不需要暴露模型私有推理。
- 新增Tool Registry：服务端保存工具名称、参数/结果契约和实现映射，决定本次模型能看见的工具说明。
- 新增Guardrail：执行前按当前用户、Run上下文和允许能力作确定性决策；工具可见性不代替这次执行授权。
- 新增Evidence与引用绑定：把命中片段、来源版本、位置和hash组织为模型可用的证据，模型引用必须能解析到本Run实际提供的证据。
- LangChain已在项目中；本章扩展其消息/工具交互用法，具体API和所用模型兼容性在实施前核对当前锁定版本。LangGraph按原路线在第六章引入复杂RAG编排，本章先把实际循环和职责讲清；如需改变引入顺序，先说明理由再调整计划。

### 数据流与不变量

```text
用户问题 → 原Thread/Run与冻结配置 → 取得本Run可见工具说明 → 调用模型
→ 模型返回工具意图 → 程序校验参数/注册信息/执行权限/预算和Run资格
→ 知识Tool：服务端范围 + 查询编码 + 已发布Dense检索 → Evidence
→ 工具结果交回模型 → 模型生成带引用的公开答案
→ 引用核对 + 原Journal/Message/Run结果事务 → SSE/页面
```

工具意图不是工具已执行；模型看见工具不等于有权限执行。用户与scope来自可信服务端上下文，不由模型/前端传入的user_id、版本ID或filter决定。工具调用/结果是本Run内部交互，不能因为调用了工具就创建新的业务Run或对话来假装恢复。

RunExecutor继续拥有执行资格、取消、绝对期限和终态；模型Adapter负责外部协议，不自行取得数据库发布/Run写入权限。工具参数、结果、来源及预算由显式Run上下文持有，不使用模块级“当前用户/最后证据”。控制面变更不重绑本次冻结配置；检索scope和Embedding配置冻结时点在5.3实施前明确，不混用向量空间。

工具/Provider失败不能冒充健康无知识；相似命中不自动证明可回答。调用重试只由已确定的一层拥有，不能给SDK、Agent循环和外层Executor各叠重试。工具产生的公开事件/结果保存失败不应通过重新提问或重跑整条Agent循环掩盖；具体保存/重试语义在接线前说明。

### 5.1 首轮讲解场景

以下为计划示意，`knowledge_search`是说明用名称，不声称当前已有该Tool/API或已调用真实模型。假设已发布文档含“每日餐费上限150元”：

1. 用户问“出差餐费每天能报多少？”
2. 模型收到可见工具的名称、用途和参数说明，提出`knowledge_search(query="出差餐费每日上限")`。
3. 程序检查工具是否注册、参数是否有效、当前用户是否获准以及本Run是否仍有资格，再执行检索。
4. Tool返回相关原文、版本和片段位置，程序把工具结果关联到对应调用，再交给模型。
5. 模型基于证据生成答案，服务端核对引用，原Run持久保存最终结果。

两个待答场景和用户实际反馈只在交接记录维护；本轮没有预填理解通过或应用编码授权。

### Registry/Guardrail 职责补讲（2026-11-11）

本项目计划里的Registry和Guardrail是模块职责，不是要求安装两个同名框架/工具包；名称可以有同名第三方产品，但不代表本项目会采用它们。实现先沿用普通Python模块、Pydantic契约和已有身份上下文，具体代码在对应授权后创建。

| 模块 | 解决的问题 | Spring职责类比 |
| --- | --- | --- |
| Tool Registry（工具注册表） | 按工具名找到说明、参数/结果契约与实际处理函数，形成本次可见工具目录 | 服务端受控的`Map<String, Tool>`或策略实现注册表 |
| Guardrail（执行护栏） | 真正调用前，依据可信用户/能力/资源范围判断本次调用是否获准；拒绝时不执行工具 | 方法调用前的业务授权检查，类似`@PreAuthorize`一类职责 |

例如模型提出知识检索请求：程序先在Registry中解析已注册工具和参数，再做本次授权，获准才调用检索实现。用户身份由服务端绑定，文档读取仍在正式Catalog/检索scope中按归属限定；入口Guardrail不代替底层范围校验。Run取消、租约和总期限仍由原执行器控制，护栏不变成另一个Run状态拥有者。

“模型看得见工具”表示它知道可提出什么调用；“本次允许执行”还取决于当前用户、具体操作和资源。允许用户A使用知识检索功能不授予读取用户B私有文档的权限。实际理解反馈及当前待答场景只在交接记录维护，本节解释不算已通过。

### 工具请求与结果如何配对（2026-11-11）

模型提出工具请求后，程序执行并把工具结果作为后续模型输入。本机已锁定的LangChain消息类型中，ToolMessage用`tool_call_id`关联工具调用；它是内部交互消息，不表示创建了新业务Run或最终用户答案。该讨论时MiniMew尚未接入这种消息；5.1 已接入内部协议和SDK回传，实际工具执行仍待5.2。

同一工具可能被调用多次，名称不足以区分“哪次调用”。例如同一Run内的示意请求分别携带`id=call_meal`和`id=call_hotel`，名称都叫`knowledge_search`，参数分别是餐费与住宿；对应结果通过相同的`tool_call_id`关联。编号示例不是当前持久化表/Contract的已定字段，也不是用户身份或新Run ID。

反馈模型时必须保留原工具请求以及与之对应的结果，不能只把两段不带关联的文本拼在用户问题后。模型收到结果后再生成公开答案；一次模型回合结束可能只是返回工具请求，业务Run仍由执行器在最终结果持久提交后终结。下一步具体协议/调用顺序和预算在实施包明确，理解反馈仍以交接记录为准。

### 5.1 模型回合协议基础包（2026-11-12）

用户对同名工具是否能只按名称配对回答“不能”，对应调用关联的讨论点确认。以下保存当时提出的5.1编码范围；用户之后明确开始，实际交付见实施记录，不能将本包扩大为整个Agent已完成。

目标是让现有模型边界能够准确表达“本回合给出文本答案”或“本回合提出工具请求”，并能在后续模型输入中带回相应工具结果。现有Provider只表达正文，若直接把工具请求当ProviderCompleted消费，会错误地把中间回合当最终答案；需先修正这个协议连接点。5.2再接工具执行，5.3接真正知识检索。

| 范围 | 具体实现/边界 |
| --- | --- |
| 内部模型输入/输出 | 普通用户/assistant消息、工具名称/描述/参数Schema、assistant工具请求及对应结果；绑定调用ID，检查缺失/重复/错配、未知工具和输入预算。模型结果明确区分文本回合与工具请求回合 |
| 单一正式Provider | 升级现有Provider与DeepSeek Adapter，迁移原调用方/受影响测试，不另开Agent HTTP入口或保留第二套正式模型路径。工具请求只是数据，不在Provider里直接运行Python函数 |
| 流与完成语义 | 工具参数流可能是多段JSON，先收齐、解析并校验后才交给上层；工具模式先收齐整个回合再判断文本/工具，避免把中间文字误写为最终答案。无工具普通聊天保持现有正文流式；模型回合结束不直接宣布业务Run完成 |
| 消息回传 | 后续请求可带原问题、assistant工具请求和匹配的工具结果，转换为现有LangChain消息。受控测试验证调用/结果正确关联，不创建产品用假工具或伪造已完成知识问答 |
| 既有执行约束 | 原RunExecutor继续控制取消、owner、绝对期限、正文持久化与终态；无工具声明的正式普通聊天仍拒绝擅自工具调用。继续关闭思考、SDK隐式重试和外部追踪，不公开私有推理或Secret |
| 验证与文档 | 定向协议/Adapter测试覆盖纯文本、参数分片、同名多调用、错配/畸形结果和缺结束确认；对受影响普通执行/取消/终态作必要PG回归。保留原断言并按单一正式协议迁移调用方，记录源码职责与实际命令/结果 |

沿用当前已锁定依赖，实施前核对其工具接口及Provider官方能力说明；本包不安装新框架，不升级数据库、不预定修改公开Event/OpenAPI或前端。新增的是内部工具交互能力，正式业务工具分派、Guardrail决策及调用循环预算属于5.2；真实文档查询编码/Dense检索属于5.3，Evidence/引用属于5.4。

本包验证以受控Provider/SDK流和隔离PG为主，不使用本机真实密钥发起收费模型请求，不消费开发库任务、不启动索引Worker、不下载模型或操作文档索引。不把“协议能表达工具请求”宣称为Agent已经能完成知识问答。本包获得明确开始反馈后连续完成，包内常规字段/测试安排自行推进；后续5.2不包含在本次授权中。

### 5.2 设计走读：一次模型回合可以提出多次工具调用

此前用户选择“先讲解其中的设计，再开始编码”，讨论当轮只写记录。以下是假设5.3接入真实检索后的教学示意，不是已经运行的知识问答。

用户A问“出差餐费和住宿标准分别是多少”。本Run第一轮模型请求携带服务端允许的工具说明；模型返回同名knowledge_search的两个请求，分别有call_meal/query餐费、call_hotel/query住宿。Registry按名称定位已注册参数契约/handler；程序整轮先校验类型、权限和剩余次数，再串行执行两次工具。权限依据服务端绑定的A和允许范围，不让模型决定用户身份；每次执行前后仍检查Run资格。两份结果使用原调用ID追加到本Run的临时模型上下文，连同原assistant工具请求再次送给模型，下一轮文本答案交由原Run终结事务保存。

这条顺利路径只有1个业务Run，实际模型请求2次、工具执行2次。模型次数和工具次数分别记录；一次模型请求可以提出多个工具请求。4次模型请求/6次工具调用是本包拟定的起始策略，不是模型天生限制，之后可据验收案例调整；总期限仍沿用原Run绝对截止时间。

如果工具都完成后下一轮模型请求发生允许重试的瞬时故障，只重试当前模型请求，复用当前上下文里的调用和结果，不从整个循环开头重做工具。该重试仍计入模型请求次数、共享剩余期限；这仅是同一执行进程中的受控重试，不代表进程重启后可恢复工具循环，后者在第七章讨论。Registry决定“叫什么/参数是什么/由谁处理”，Guardrail决定“本次允许执行吗”，循环决定“下一步及剩余额度”，原执行器继续拥有取消、资格和持久终态。

这里复用的依据是“本次工具执行已经成功，且结果仍在当前Run上下文中”，不是工具永远返回固定值。数据库记录、天气等可随时间变化；再次查询可能得到另一份结果。当前模型请求重试时沿用已取得结果，避免无意重复工具执行或更换这次回答的依据；新Run或明确规划的新工具调用可以重新查询，不推导跨Run缓存规则。

### 5.4 首轮架构讨论（2026-11-12）

本节是用户在5.1–5.3本地合并提交`1760cae`后回复“继续”所进行的设计讲解，不是5.4编码授权。以下新增模块、编号语法及存储结构均为建议，不描述为已交付，也不预填用户已理解或同意选型。

**整体位置**：5.3的`KnowledgeMatch`已经携带Document/Version/chunk、原文、位置、hash和相似度，但尚无本Run的可引用身份，也没有最终答案引用检查。检索命中是候选；Evidence是组织了身份和来源的可引用材料；答案引用是答案中指向Evidence的关联，三者不是三个独立服务。

建议的数据流：原Run工具循环 → 既有知识检索 → 按结果预算选定完整片段 → 本Run Evidence目录登记 → 带引用编号的工具结果回传模型 → 模型生成含编号的答案 → 服务端解析校验 → 原终结事务保存答案、引用映射与所需Evidence快照 → 历史/API/SSE供前端读取。新增的是现有API内的业务模块，不新增进程、检索引擎或模型框架。

例如，`E1`指向旧版V1的“每日餐费150元”片段，答案写“每日上限150元。[E1]”。`E1`仅为讲解用编号，正式格式和Contract待实施包确定；持久定位须结合Run及完整来源身份，不能只凭短编号。模型不用自行填写文档UUID或拼接链接，服务端从本Run目录解析出处。

| 模块 | 职责与拆分理由 |
| --- | --- |
| 既有`knowledge.py` | 保持用户范围、查询编码、Dense检索与结果预算；在已选定可回传的原文上接入Evidence登记，不把所有被预算剔除的候选变成可引用材料 |
| 建议新增Evidence目录 | 为本Run分配稳定引用编号、按来源身份与实际提供内容去重，保留原文/版本/位置/hash；重复检索排序变化不使已有编号改指别处，跨Run不共享可变目录 |
| 建议新增答案引用校验 | 在`execution/service.py`的`_generate`接收最终text后、进入原终结事务前解析引用；只将能解析到本Run实际提供材料的引用认定为有效，不让Provider承担业务来源与授权规则 |
| 既有Repository/Journal及后续查询投影 | 在原执行资格与终态规则内持久保存结果，刷新后能读取相同来源；不增加第二条宣布Run成功的路径 |

**持久化建议与代价**：仅将目录放在`KnowledgeSession`内存里不能支持历史引用。可保存指向不可变PG索引产物的引用，也可保存有预算的实际提供原文快照。首轮建议后者加完整来源身份，便于准确还原模型看到的材料，代价是额外存储。答案与所需快照/引用映射由原终结事务一致保存；运行中的目录仍属本Run，这不等于实现进程重启恢复，后者在第七章。具体表、唯一约束、读取权限、错误契约及生成物需在编码包确定。

旧版向量未来可被清理，新版也可发布，因此查看历史引用不能重新检索“当前文档”，应读取保留的不可变来源/证据快照。用户/Run归属检查仍在服务端读取链路执行，短引用编号不赋予访问权。

**模型输出方案**：首轮建议沿用当前text回合，约定受控引用标记，由服务端解析成结构化引用信息，避免立即扩展Provider为新的结构化答案协议。该取舍保留普通聊天与原执行链，但需明确定义标记语法及校验规则；未引用、无知识、格式错误等处理策略尚待具体工作包讨论。结构化最终答案是另一方案，需要验证所用Provider能力并修改协议，不能声称当前已支持。

5.4解决“引用身份真实、版本可定位、历史可重现”；合法引用不自动证明答案每个结论均被原文支持。证据充分性、语义评判、重写和评测仍属于后续章节。5.4先形成后端证据/引用能力及必要契约，5.5再接过程与引用界面。沿用Python/Pydantic、SQLAlchemy/PostgreSQL和既有Contract生成链；Evidence是领域设计，不是新安装的包。

本轮仅保存讨论和交接记录，未改应用代码、Contract、迁移、依赖或配置，未运行模型/数据库/业务测试，不创建小章节完成提交。

### 5.4 第二轮架构走读（2026-11-12）

用户再次“继续”，本轮仍为设计讨论，无5.4编码授权。以“餐费与住宿各能报多少”为例：同一个Run可能先查询餐费，再查询住宿，最后组合答案；工具调用ID关联某次请求与结果，Evidence引用ID关联答案与来源，不能混用。一次工具调用可返回多个Evidence，同一个Evidence也可能出现在多次检索结果中。

| 同一Run内的步骤 | 状态与职责 |
| --- | --- |
| 执行器领取并创建上下文 | 沿用原Run与模型快照；建议为这次执行建立Evidence目录，不能存在全局“最近一次证据” |
| 首次知识查询 | 既有KnowledgeSession固定published scope；它决定允许查询哪些已发布版本，不等于最终引用清单 |
| 返回餐费片段 | 建议对最终能装入工具结果/模型上下文的片段注册E1；与知识Tool结果一起送回模型 |
| 再次查询住宿 | 继续使用同一scope；新片段注册E2，重复的相同来源/内容复用已有编号，E1不因新排序改变 |
| 模型组合答案 | 例如“餐费150元[E1]；住宿500元[E2]”，金额仅为走读示例 |
| 服务端终结 | 解析引用并形成结构化结果，原终结事务一致保存正文、所需Evidence快照及引用映射；之后由历史接口和Journal投影读取 |

**两份目录的差异**：检索scope在第一次知识查询时固定，表达本Run可查的版本范围；Evidence目录随着成功提供的材料增加，表达实际给模型看过的来源。scope不是Evidence，也不能把scope中所有文档标为答案依据。一次调用回传预算、跨调用累计Evidence预算、整个模型上下文预算需要衔接，不能因有6次工具额度就假定6份最大结果一定装得下；本轮仅讨论设计，具体限额未定。

**代码接线建议**：沿用`ToolContext`/每Run工具会话传递目录，在`knowledge.py`接入登记；在`execution/service.py`中于工具结果追加上下文、最终text返回的位置接线。当前`_generate`返回str、`_finish`传递正文/错误，需在5.4编码包中改为显式传递答案与引用的数据对象；不能靠执行器实例字段偷偷保留“本次引用”，因为Dispatcher会并发执行多个Run。

**两种消息的区别**：tool_call_id关联的assistant/tool消息目前保存在本次模型上下文；它们不是新增业务Message行。业务历史仍是原用户Message和assistant Message；引用属于后者的答案数据，不能为了每次检索创建新Thread、Run或聊天Message。

**持久与展示**：Evidence快照保存可定位原文，引用映射保存答案使用了哪些来源及其编号。建议历史响应与最终事件采用一致的结构化引用投影，原文详情按身份校验后读取，避免前端分别从正文猜测链接和自行拼装版本。具体schema/版本策略、迁移与生成输出在实施包明确；不手改生成类型。第五章不因此实现完整工具执行审计或Checkpoint重启恢复。

**产品选择已确认**：用户明确选择“混合回答：允许补充模型知识，但必须与有文档引用的内容清楚区分”。因此答案设计应区分带真实Evidence引用的文档依据与明确标注的模型补充；后者不能伪装成资料原文，也不能为了显示出处而挂上无关引用。当前工具仍是auto选择，知识能力开启不等于每个问题都会检索；本次选择没有要求所有问题强制调用检索，也不授权新增界面模式。

**工具观测链**：执行器已通过Registry/Guardrail并取得执行资格 → 原Repository短事务追加公开工具开始事件/Outbox → 执行原handler → 短事务追加公开工具结束/失败事实 → 原模型循环继续。SSE/Redis仍沿用既有Journal路径；前端reducer按sequence与tool_call_id重放投影。工具调用完成只表示该工具结果已取得，不等于Run成功；失败/取消/中断由原Run终态结算，未闭合的工具状态不能永久显示运行中。界面只展示工具名及受控状态/错误摘要，不公开参数JSON、原始结果或模型私有推理。

当前v1没有工具过程事件，PG亦有限制Event type的约束，不能只改前端switch或在运行状态里猜测。收尾包需扩展正式事件Contract/生成器/前后端消费者、相关PG约束与迁移，保持既有message.completed形状、sequence规则及历史事件可读；具体事件名称和兼容规则在实现前确定。Journal继续作为公开观测事实来源，不另建绕开Run的进度轮询接口或全局当前工具。状态事件保存的幂等与失败重试应留在原执行资格内，不因补记事件重新执行已成功工具，也不假称具备进程重启恢复能力。

## 结章文字总结（2026-11-13）

第五章把第四章的“可检索文档”接成了可观察、可追溯的基础Agent知识问答。模型可以提出工具请求，但Registry决定工具定义/参数/实现映射，Guardrail在执行前检查授权，原RunExecutor负责推进有限模型/工具回合与取消/期限，Provider只转换外部模型协议。模型多次调用不增加业务Run或额外聊天Message。

知识工具从服务端上下文绑定用户，首次查询固定已发布版本范围；查询向量与索引使用相同的冻结编码空间。Milvus提供候选，程序核验来源并投影原文，在预算内登记Run私有Evidence身份。模型获得带编号材料后生成文档依据与明确标识的模型补充，服务端检查引用身份和位置，再由原事务一致保存Message、引用快照、完成事件/Outbox及Run终态。这里新增的是领域对象和业务模块，没有为每个术语引入新服务。

引用展示和执行过程使用不同读取链：前者读原/answer的持久快照，后者重放Journal中的公开工具事件。浏览器与Redis都不拥有执行事实，断连不会取消Run；重复通知/事件不会重复追加工具展示。旧版向量清理和新版发布不改变历史依据，换账号/Thread不会带回旧缓存。引用载入失败只影响来源展示，不能把已完成回答改成失败。

本章的关键取舍是：先用明确有界循环讲清Agent职责，复杂LangGraph路由留第六章；知识工具模式先缓冲完整回合，普通聊天保留流式；引用使用服务端编号与原文快照，增加少量存储以换取历史可重现；工具观测留在同一Journal而非新建第二套进度事实；允许混合回答但必须区分来源与补充。Provider/检索故障明确失败，不用模型常识静默掩盖故障；事件确认丢失只补记记录，不重做已成功工具。

当前验收证明协议、事务、权限、版本定位、重放及界面链路；不能证明真实DeepSeek每次都正确选工具、引用语义充分或答案质量达标。复杂召回/融合/重排、证据语义评判与一次改写在第六章，HITL/Checkpoint进程重启恢复在第七章，产品化评测闭环在第八章。用户已选混合回答并授权完成本包，不据此填写用户已完全掌握后续概念。

| execution/messages.py、provider.py、deepseek.py | 表示模型内部消息/工具请求/回合及服务端指令，转换真实SDK流 | 使用本Run冻结模型快照，隐式重试关闭；不是业务Message表或新Run |
| execution/tools.py | 严格参数/结果、Registry、Guardrail、ToolContext | 注册目录可共享；能力、用户范围、工具会话与Evidence目录属于Run |
| execution/service.py | 在同一Run内反复调用模型/工具，控制4/6预算和绝对期限 | 显式传递上下文、结果、观测与AnswerResult；不持有跨网络长事务 |
| knowledge.py、knowledge_runtime.py | 绑定published scope、编码query、复用Dense检索并返回原文 | 重模型/只读连接由API lifespan共享且有界准入；用户scope不放共享Runtime |
| documents/retrieval.py、embeddings、vector_store | 延用第四章目录/编码空间/候选核验与Milvus Adapter | Worker独立构建，API只读已发布范围；Milvus不替代PG发布目录 |
| evidence.py | Run内编号、去重/预算、混合答案与引用校验 | 纯业务模块；不连接DB，不冒充语义Grader |
| execution/repository.py、journal.py、models.py | 执行资格、观测幂等、最终Message/答案材料/事件/Outbox事务 | PG为事实来源；旧owner不能写，终态唯一；引用快照不复制权威正文 |
| answers.py | 带归属校验读取原Message与不可变来源映射 | 单SELECT快照及一致性检查；不重新向量检索，不产生新模型调用 |
| frontend/src/answers.ts、stores/chat.ts | 严格解析、码点切分、当前身份下的请求/缓存与历史/订阅 | 只在内存保存当前视图，令牌续期沿原认证；迟到响应不回填 |
| frontend/src/events | 从正式Contract检查Event，按Run/sequence投影正文/工具/终态 | 重复丢弃、缺口补读；投影不是执行事实源 |
| ChatPanel.vue、AnswerBody.vue、ToolActivity.vue | 显示聊天、依据/补充、原文与工具过程 | 组合既有store状态，不执行工具、拼造来源或宣布后端终态 |
| examples/rag/chapter05-cases.json、相关tests与浏览器脚本 | 有限固定案例和正式路径的受控/真实基础设施证据 | 不接入生产执行，不是第八章评测平台 |

代表性请求：用户提问进入api/runs.py → conversations预留原Run/消息及快照 → Dispatcher领取 → service调用Provider → Registry/Guardrail分派knowledge_search → knowledge固定scope/编码/检索并登记Evidence → tool结果回传模型 → evidence解析混合答案 → Repository原子保存 → Journal/SSE/reducer呈现过程与终态 → chat store通过/answer载入引用 → AnswerBody显示保存版本的原文。API内这些是模块/后台任务；独立进程仍是Indexing Worker，PG/Redis/Milvus仍是原共享基础设施。

```text
聊天页 ChatPanel / Pinia
  ├─ 提问 → API → PG预留Thread / Run / Message / Model Snapshot
  ├─ 订阅 ← SSE ← Event Journal ← 工具观测与原终结事务
  └─ 引用 → /answer → PG里的Message + AnswerRecord快照

API后台 Dispatcher → 领取事务 → RunExecutor（同一个Run）
  ├─ Provider：模型回合 / 工具意图 / 最终文本
  ├─ Registry + Guardrail → KnowledgeService
  │                          ├─ published scope：PG已发布版本范围
  │                          ├─ 查询Embedding → Milvus Dense检索
  │                          └─ Run Evidence → 工具结果 → 下一模型回合
  └─ 答案解析 → 原终结事务 → Message + 引用快照 + Journal/Outbox

独立 Indexing Worker → 解析/分块/编码/索引核验 → PG原子发布指针
Redis ← Outbox发送提醒；SSE被唤醒后仍从PG读事实
```
